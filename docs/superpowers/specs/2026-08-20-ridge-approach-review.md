# RidgeDivider 능선 오버레이 — 아키텍처 재검토

날짜: 2026-08-20
범위: 설계 판단만. 코드 변경 없음.

## 1. 문제의 정확한 형태

`RidgeDivider`(`website/src/components/visuals/ForestLetterMotifs.tsx:24`)는 `viewBox 0 0 1440 96`의 SVG 물결 path를 `fill="currentColor"`로 채우는 장식 요소다. `Footer.tsx:30-32`에서 `relative h-0` 래퍼 안에 `absolute -bottom-px`로 배치되어, 레이아웃 높이를 차지하지 않고 **앞 섹션 위에 불투명하게 겹쳐 그려진다.** 높이는 `h-10 sm:h-14 md:h-20`(40/56/80px), 파형이라 실측 크레스트는 breakpoint별로 다르다(주석 기준 sm 42px, md 60px, 어떤 페이지 주석은 md 80px로 다르게 적어놓음 — 이것 자체가 이미 값이 한 곳에 정의돼 있지 않다는 증거).

두 구현을 낳은 진짜 원인을 구분해야 한다:

- **버그 A (색상 이음매)**: flow 배치 시, divider의 투명 영역이 `<footer>`의 형제인 `<body>` 배경(크림)을 비춘다. `<main>`의 마지막 섹션이 무슨 색이든 상관없이 항상 크림이 보인다.
- **버그 B (콘텐츠 잘림)**: overlay 배치는 버그 A를 완전히 없애지만, `fill="currentColor"`가 불투명하므로 **앞 섹션의 실제 콘텐츠(카드, 텍스트, 버튼)가 그 자리에 있으면 그대로 덮인다.** 색이 우연히 같아도(홈 마지막 섹션 `--color-deep` 위에 `--color-deep` 물결) 잘림 자체는 없어지지 않는다 — 안 보일 뿐 여전히 잘려 있다. 텍스트가 그 60px 안에 있었다면 홈페이지에서도 잘렸을 것이다.

지금 겪고 있는 것은 버그 B이고, 이건 색상 문제가 아니라 **"여백 예약"** 문제다. 이 구분이 아래 평가 전체의 축이다.

## 2. 코드에서 확인한 사실

- `PublicShell.tsx:20-29`: `<main>{children}<CustomSectionsHost /></main>` 다음에 바로 `<Footer />`. `CustomSectionsHost`가 항상 `<main>`의 **진짜 마지막 자식**이다.
- `CustomSectionsHost.tsx:55-168`: 관리자 빌더로 추가되는 커스텀 섹션. 배경은 3종 테마(`forest`=`--color-forest` 진초록, `sand`=`--color-bg-warm`, 기본=흰색) 중 admin이 고른다. **개발자가 절대 건드리지 않는 컴포넌트이고, 여기엔 능선 여백에 대한 언급이 전혀 없다.**
- `HomeClient.tsx:110`: 홈의 실제 마지막 섹션 배경은 `bg-[var(--color-deep)]` — 풋터와 정확히 같은 색. 여기서 겹침이 "안 보이는" 이유는 딱 이 한 페이지, 이 한 색 조합에서만 우연히 성립한다.
- `TimelineCta.tsx:7-9`, `board/page.tsx:48-49`, `gallery/page.tsx:162-163`: 세 곳 모두 "능선이 몇 px 겹쳐도 안 가리게" 여백을 손으로 맞춘 주석이 있고, 값이 서로 다르다(md 60px vs md 80px vs sm 42px). 코멘트에 적힌 실측값 자체가 파일마다 어긋나 있다는 것은 단일 소스가 없다는 직접 증거다.
- `press/page.tsx`는 이런 주석/보정이 아예 없다 — 카드가 잘리는 현재 버그가 발생한 페이지.

## 3. 옵션별 평가

### 옵션 1 — 오버레이 유지, 여백을 전역 한 곳에서 예약

`PublicShell`의 `<main>` 끝에 고정 높이 스페이서를 넣는 안. 문제는 스페이서 자체의 배경색이다. 배경 없이(투명) 넣으면 버그 A가 그대로 재발한다(홈처럼 마지막 섹션이 어두우면 크림 띠가 다시 생김). 배경을 항상 크림으로 고정해도 마찬가지. **즉 "전역 한 곳"만으로는 두 버그를 동시에 못 없앤다** — 스페이서가 마지막 섹션이 실제로 어떤 색인지 알아야만 성립한다. 이게 프롬프트가 지적한 홈페이지 반례가 정확히 가리키는 지점이다.
→ 색 인식 메커니즘과 결합하지 않으면 미완성. (§4에서 결합안 제시)

### 옵션 2 — flow로 복귀 + 앞 섹션 색 상속

CSS 변수/`:has()`/footer prop으로 "앞 섹션 색"을 divider에 흘려보내는 안. 순수 CSS `:has()`만으로는 "직전 형제가 마지막에 렌더된 임의 배경색"을 일반화해서 잡을 수 없다(대상이 무한히 다양한 임의 컴포넌트라서). 결국 각 마지막 섹션이 "내 색은 X"라고 명시적으로 선언해야 하고, 그 선언을 footer까지 전달할 매개체가 필요하다 — React Context나 CSS 커스텀 프로퍼티를 부모 요소에 세팅하는 정도. 실현 가능하지만 그 자체로는 버그 B(콘텐츠 잘림)를 안 고친다 — flow 배치로 돌아가면 다시 real height를 차지하니 잘림은 없어지지만, 그러면 결국 §4와 사실상 동일한 결론(여백은 실제로 차지해야 하고, 색은 선언받아야 함)에 도달한다. 즉 "2번은 색을, 1번은 공간을" 풀지만 **완전한 해법은 둘의 결합**이다.

### 옵션 3 — 능선을 더 짧게(또는 겹침을 무시할 만큼 작게)

크레스트를 30px로 줄이면 잘리는 확률은 낮아지지만 **없어지지 않는다.** 지금 버그가 난 `/press` 카드도 "우연히 그 페이지가 60px 안에 걸렸다"일 뿐, 30px이었어도 다른 페이지 다른 콘텐츠가 그 30px 안에 걸릴 수 있다. 이건 버그의 확률을 낮추는 완화책이지 클래스를 없애는 해법이 아니다. 게다가 시각적으로도 "산이 솟아오르는" 효과가 죽는다 — 지금 md 80px 크레스트가 디자인 의도인데 그걸 줄이면 장식 자체의 존재 이유가 약해진다. 기각.

### 옵션 4 — 능선을 풋터 자기 자신의 모양(mask/clip-path)으로

풋터의 상단 테두리 자체를 물결로 깎아내는 안. 직접 검토해보면, clip-path로 풋터 박스 상단을 잘라내도 "잘려나간 영역 바깥에 뭐가 보이는가"라는 질문은 그대로 남는다 — 풋터가 in-flow로 실제 높이를 차지하고 겹침이 전혀 없다면, 잘려나간 영역은 여전히 `<body>` 배경(크림)을 드러낸다. 즉 **flow 배치인 이상 옵션 2와 동일한 색 상속 문제로 귀결**되고, overlay로 만들면(잘린 영역이 앞 콘텐츠 위에 겹치게) 옵션 1과 동일한 잘림 문제로 귀결된다. mask/clip-path는 "SVG path냐 CSS shape냐"의 구현 디테일 차이일 뿐, 겹칠지 안 겹칠지의 근본 트레이드오프를 바꾸지 못한다. 순수 CSS 구현이라는 장점은 있지만 문제의 본질을 옮기지 않는다.

### 옵션 5 — 능선이 안전한 페이지에서만 사용

"안전한 배경색을 가진 페이지 목록"을 만들고 거기서만 능선을 켜는 안. 정적 페이지 한정으로는 그럭저럭 가능(지금의 `nav-routes.ts` 패턴과 같은 방식). 하지만 **관리자 빌더로 커스텀 섹션이 추가되는 순간 리스트가 틀린다** — `CustomSectionsHost`가 페이지의 새 "마지막 섹션"이 되는데, 이건 런타임에 admin이 결정하는 데이터라 빌드 타임 화이트리스트로 못 잡는다. 이 옵션은 프롬프트가 명시한 바로 그 실패 조건(빌더로 섹션을 추가하는 순간 아무도 여백을 안 챙겨준다)에 정확히 걸린다. 기각.

## 4. 권장안 — 옵션 1 + 옵션 2의 결합: "여백은 전역에서 실제로 예약하고, 색은 마지막 섹션이 선언한다"

오버레이 자체(위로 겹쳐 그리는 방식)는 유지한다. 버그 A를 근본적으로 없앤 유일한 방식이고, 시각 효과(산이 솟아오르는 느낌)도 이 방식이라야 나온다. 문제는 오버레이가 아니라 **"여백 예약과 색 선언이 페이지마다 수동"**이라는 점이다. 그러니 이 둘을 각각 한 곳으로 모은다.

1. **여백은 `PublicShell`의 `<main>`이 끝에서 한 번만 예약한다.** `children` + `CustomSectionsHost` 뒤에, 능선과 정확히 같은 높이(`h-10 sm:h-14 md:h-20` — `RidgeDivider`와 상수를 공유)의 빈 스페이서 div를 추가한다. 이 안에는 어떤 페이지의 마지막 섹션도 콘텐츠를 놓을 수 없으므로(스페이서는 항상 빈 요소), 오버레이가 그 위에 겹쳐 그려져도 **잘릴 콘텐츠 자체가 없다.** 지금 페이지마다 손으로 넣은 `pb-*` 보정들은 전부 걷어낸다 — 정확히 이 스페이서가 하던 일을 각 페이지가 중복해서 흉내 내고 있었을 뿐이다.
2. **색은 마지막 섹션이 선언한다.** 정적(개발자 작성) 페이지는 이미 있는 `nav-routes.ts`와 동일한 패턴으로 `footer-ridge-colors.ts` 같은 라우트→색 매핑 테이블을 하나 둔다(기본값은 `--color-bg` 크림, 명시된 라우트만 override — 예: `/` → `--color-deep`). 정적 매핑이라 서버에서 바로 결정되고 깜빡임이 없다. `CustomSectionsHost`는 예외로 취급한다 — 이미 `section.theme`으로 마지막 섹션의 배경을 알고 있으므로, 커스텀 섹션이 1개 이상 존재하면 그 컴포넌트가 (작은 Context나 `main`에 CSS 변수를 세팅하는 방식으로) 정적 매핑을 override한다. **admin은 아무것도 몰라도 된다** — 이미 고르고 있는 forest/sand/기본 테마 선택이 그대로 능선 색깔 선언이 된다.
3. 스페이서의 `background`는 이 색 값을 그대로 쓴다. 오버레이(능선)는 지금처럼 `--color-deep`로 칠하되, 스페이서 배경이 마지막 섹션과 같은 색이면 이음매가 없고, 다르면(정적 페이지 대부분처럼 크림) 원래도 자연스러운 크림→능선 전이가 된다.

### 이 안이 버그 클래스를 없애는 이유

- 콘텐츠 잘림(버그 B)은 **레이아웃 차원에서 원천 차단**된다 — 스페이서가 항상 마지막에 있고 항상 비어 있으므로, 어떤 새 페이지·새 컴포넌트·새 admin 섹션이 추가돼도 "그 콘텐츠가 우연히 마지막 60px 안에 있는가"라는 질문 자체가 사라진다.
- 색 이음매(버그 A)는 **선언을 깜빡해도 최악의 결과가 크림 대 실제색 seam 하나**로 그친다 — 지금처럼 콘텐츠가 물리적으로 잘리는 것보다 훨씬 관대한 실패 모드다. 그리고 정적 페이지의 기본값(크림)이 애초에 사이트 대다수 페이지의 실제 마지막 배경과 같으므로, 대부분 페이지는 아무 것도 선언할 필요가 없다.
- admin 빌더 케이스가 명시적으로 처리된다 — 이게 다른 모든 옵션이 무너지는 지점이었다.

### 이 안의 비용

- 새 파일: `footer-ridge-colors.ts`(라우트→색 매핑, `nav-routes.ts` 패턴 그대로 복붙 수준), 작은 Context 또는 `useLayoutEffect`로 CSS 변수 세팅하는 훅(커스텀 섹션 override용).
- 수정: `PublicShell.tsx`(스페이서 추가, 색 결정 로직 연결), `CustomSectionsHost.tsx`(override 등록 1줄), `ForestLetterMotifs.tsx`(높이 상수를 공유 가능하게 export).
- 되돌리기: `TimelineCta.tsx`, `board/page.tsx`, `gallery/page.tsx`의 수동 `pb-*` 보정과 주석 제거, `press/page.tsx`는 원래 보정이 없었으니 그대로 두면 스페이서가 알아서 커버.
- 리스크: 커스텀 섹션 override에 Context/이펙트를 쓰면 첫 렌더는 기본색(크림)으로 그려졌다가 이펙트 이후 실제색으로 바뀌는 짧은 깜빡임이 admin 빌더 페이지에서만 발생할 수 있다. 이는 감수할 만하다 — 발생 범위가 좁고(빌더로 어두운 마지막 섹션을 추가한 페이지에서만, 그것도 첫 페인트 직후 한 프레임), 결과가 색 seam 정도지 잘림이 아니다.
- 규모: 중간(Small~Medium) — 새 파일 1~2개, 기존 파일 4~5개 수정, 로직 자체는 얕음(라우트 매핑 + 높이 상수 공유 + 스페이서 div 하나). 하루 미만 작업으로 예상.

### 지금 깨진 페이지에 대한 조치

`/press`는 스페이서가 생기는 즉시 저절로 고쳐진다(카드 밑에 실제 공간이 생기므로). 앞서 154px 죽은 여백이 생겼던 페이지는, 원인이 "외부 래퍼 padding + 내부 요소 padding 중복"이었던 만큼, 그 페이지의 수동 padding들을 이번 기회에 전부 제거하고 전역 스페이서 하나로 대체하면 중복 자체가 구조적으로 재발 불가능해진다.

## 5. 이 결론을 뒤집을 증거

- **관리자 빌더 섹션이 실제로는 매우 드물게 쓰이고(예: 지금 운영 중인 페이지 0곳), 향후에도 안 쓰일 계획이 확정**되어 있다면, 옵션 5(정적 페이지 화이트리스트)로도 실질적 위험이 없다 — 이 경우 전역 스페이서+색 선언 인프라를 만드는 비용이 과할 수 있다. `custom-sections` 관련 admin UI가 실제 활성 라우트에서 몇 번이나 저장됐는지 데이터로 확인해볼 가치가 있다.
- **디자인상 능선이 앞 섹션과 정확히 겹쳐도 무방하다**(즉 "산이 콘텐츠를 살짝 덮으며 솟아오르는" 게 의도된 그래픽 효과이지 버그가 아니다)는 결정이 내려진다면, 지금의 per-page 보정 자체가 정답이고 이번 리뷰의 전제(잘림=버그)가 틀린 것이다. 다만 `/press` 카드 잘림처럼 실제로 클릭 가능한 UI 요소나 텍스트가 가려지는 경우까지 "의도된 효과"로 보긴 어렵다.
- **`RidgeDivider`의 크레스트 높이가 이미 반응형 CSS만으로 각 마지막 섹션의 실제 배경색을 안정적으로 상속받을 방법**(예: 향후 CSS `if()`/커스텀 프로퍼티 상속 스펙 발전, 또는 Tailwind v4의 새 기능)이 생긴다면 별도 Context/매핑 없이 순수 CSS로 옵션 2를 완성할 수 있어 이번 권장안의 Context 부분은 불필요해진다 — 그때는 여백 예약(스페이서)만 남기고 색 로직은 걷어내면 된다.
